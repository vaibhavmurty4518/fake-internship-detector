# Fake Internship Detector

**Formal title:** Machine Learning-Based Detection and Risk Assessment of Suspicious Internship Postings

A working ML prototype that lets a user paste an internship/job posting and get back a
**risk level (LOW / MEDIUM / HIGH)**, a **risk score**, a list of **suspicious indicators**,
and a **plain-English explanation** — all generated by a trained classifier plus a
transparent, rule-based explainability layer (not a black box "fake = 1").

---

## 1. Project Overview

Online internship scams (fake postings that ask for registration fees, promise unrealistic
pay, or pressure applicants with urgency) are a growing problem, especially for students who
are actively looking for their first work experience and are less familiar with typical
red flags. This project builds a supervised machine-learning system that screens a pasted
posting and flags suspicious characteristics, so a student gets a **second opinion before
acting** on an offer.

## 2. Problem Statement

Given the raw text of a job/internship posting, predict whether it exhibits characteristics
associated with fraudulent postings, and explain **why**, using both a trained text
classifier and explicit rule-based indicators (payment requests, urgency language, unusual
compensation, missing company information, etc.).

## 3. Objectives

- Train and compare multiple classical ML models on a real, publicly available
  fraudulent-job-postings dataset.
- Engineer both textual (TF-IDF) and structured, explainable features.
- Select the best model using proper train/test evaluation (accuracy, precision, recall,
  F1, confusion matrix) — no fabricated numbers.
- Build a usable, demo-ready Streamlit interface with a clear risk output and explanation.
- Respect ethical constraints: never assert a company "is fake"; always frame output as a
  risk indicator requiring human verification.

## 4. Scope

This is an **academic prototype**, not a production fraud-detection system. It performs
**preliminary heuristic + ML-based screening** of pasted text. It cannot verify a company's
real-world legitimacy (registration records, physical address, etc.) — that requires human
/ institutional verification, which the UI explicitly states.

## 5. Technology Stack

| Layer | Tools |
|---|---|
| Language | Python 3.9+ |
| Data handling | Pandas, NumPy |
| ML | Scikit-learn (Logistic Regression, Random Forest, Linear SVM) |

## 6. Dataset

**IMPORTANT — read this section before the demo.** This project does **not** use an
internship-exclusive dataset, because no sufficiently large, labeled, public
*internship-only* fraud dataset exists. Instead it uses the most widely used public dataset
for this problem family and **adapts it into an internship-focused prototype**, exactly as
instructed.

- **Dataset name:** Employment Scam Aegean Dataset (EMSCAD), distributed on Kaggle as
  *"Real or Fake Job Posting Prediction"*.
- **Original source:** University of the Aegean, Laboratory of Information & Communication
  Systems Security — http://emscad.samos.aegean.gr/
- **Kaggle mirror used for this project:** https://www.kaggle.com/datasets/shivamb/real-or-fake-fake-jobposting-prediction
  (the CSV used here, `data/dataset.csv`, was obtained from a public GitHub mirror of the
  same Kaggle file, matched column-for-column and row-count-for-row-count against the
  published dataset statistics — 17,880 rows, 17,014 legitimate / 866 fraudulent — to
  confirm it is the authentic file, not a fabricated one).
- **License / usage considerations:** EMSCAD was released by the University of the Aegean
  for academic research into recruitment fraud; the Kaggle mirror is widely used for
  non-commercial, academic ML coursework and research (as evidenced by dozens of public
  university/course projects built on it). This project uses it strictly for a non-commercial
  academic assignment. **Before any redistribution or commercial use, verify the current
  license terms on the Kaggle dataset page.**
- **Number of records:** 17,880 job postings, of which 866 (4.8%) are labeled fraudulent —
  a realistically **imbalanced** dataset, handled explicitly (see Methodology).
- **Important columns used:** `title`, `company_profile`, `description`, `requirements`,
  `benefits`, `telecommuting`, `has_company_logo`, `has_questions`.
- **Target column:** `fraudulent` (0 = legitimate, 1 = fraudulent).

### Honest limitation: general jobs, not internships-only

Only ~581 of the 17,880 postings (~3.2%) have "intern" in the title, and only 3 of those
are labeled fraudulent — too few to train a reliable model on internships alone. So the
model is trained on the **full dataset of general job/internship postings** (the scam
patterns — fee requests, urgency, unrealistic pay, personal-email contact — are the same
across job and internship scams), and the prototype is framed and evaluated as an
**internship-focused screening tool built on a general recruitment-fraud dataset**. This
is stated explicitly here and in the Limitations section rather than being hidden.

## 7. Methodology (Engineering Workflow)

```
Problem Definition → Requirements → Data Collection → Data Preprocessing
    → Feature Engineering → Model Development → Testing → Evaluation
    → Deployment (Streamlit Prototype) → Iterative Improvement
```

1. **Data Collection** — `data/dataset.csv` (EMSCAD, see above).
2. **Preprocessing** (`preprocess.py`) — HTML-tag stripping, lowercasing, non-alphabetic
   character removal, stopword removal, whitespace normalization.
3. **Feature Engineering** (`feature_engineering.py`) — see Section 8.
4. **Model Development** (`train_model.py`) — TF-IDF (unigrams+bigrams, 4000 features) is
   combined with 17 scaled structured features into one feature matrix; three classifiers
   are trained with `class_weight="balanced"` to handle the 95%/5% imbalance.
5. **Testing / Evaluation** — stratified 80/20 train-test split, metrics computed only on
   the untouched 20% test set (see Section 10).
6. **Deployment** — `app.py`, a Streamlit prototype.
7. **Iterative Improvement** — see Section 15 (Future Scope).

## 8. Feature Engineering

**Text feature:** TF-IDF over the combined `title + company_profile + description +
requirements + benefits` text (unigrams + bigrams, top 4000 terms).

**Structured, explainable features** (`feature_engineering.py`), computed identically at
training time and inference time so the live app matches the trained model exactly:

| Feature | What it captures |
|---|---|
| `fee_flag` / `fee_count` | Registration/processing fee, deposit, "pay to apply" language |
| `urgency_flag` / `urgency_count` | "Limited seats", "apply today", "hurry", etc. |
| `suspicious_phrase_count` | "No experience needed", "guaranteed income", "100% job guarantee" etc. |
| `high_amount_flag` | A guaranteed monthly figure above a heuristic threshold (₹40,000 or $1,500) — **a heuristic threshold, not derived from the dataset's salary column**, because that column is too sparse/inconsistent across currencies to define a reliable "expected range" (see code comments in `feature_engineering.py`) |
| `personal_email_flag` | Contact requested via Gmail/Yahoo/Hotmail/etc. instead of a company domain |
| `whatsapp_flag` | Contact requested via WhatsApp |
| `phone_count`, `url_count` | Presence of phone numbers / external links |
| `exclamation_count`, `uppercase_ratio` | Excessive punctuation / shouting text |
| `length_chars`, `length_words` | Posting length |
| `telecommuting`, `has_company_logo`, `has_questions` | Optional meta-data flags, mirrored from the dataset columns, collected via checkboxes in the UI |
| `low_company_info_flag` (UI-only, explainability layer) | No "about us"/company-profile-style content found |

## 9. ML Models Compared

- Logistic Regression (`class_weight="balanced"`)
- Random Forest (250 trees, `class_weight="balanced"`)
- Linear SVM (`LinearSVC`, `class_weight="balanced"`, wrapped in `CalibratedClassifierCV`
  for probability outputs)

All three are trained on the identical TF-IDF + structured feature matrix, on the identical
80/20 stratified split (`random_state=42`), so the comparison is apples-to-apples.

## 10. Evaluation Results (real numbers from `models/metrics.json`)

Dataset: 17,880 postings → 14,304 train / 3,576 test (stratified 80/20).
Because the dataset is ~95% legitimate / ~5% fraudulent, **accuracy alone is misleading**
(a model predicting "legitimate" for everything would score ~95% accuracy while being
useless). The model was therefore selected by **F1-score on the fraudulent (minority)
class**, not by raw accuracy.

| Model | Accuracy | Precision (fraud) | Recall (fraud) | F1 (fraud) | F1 (macro) |
|---|---:|---:|---:|---:|---:|
| Logistic Regression | 95.61% | 52.68% | 90.75% | 0.6667 | 0.8216 |
| Random Forest | 97.93% | 100.00% | 57.23% | 0.7279 | 0.8586 |
| **Linear SVM (selected)** | **98.41%** | **90.85%** | **74.57%** | **0.8190** | **0.9054** |

**Selected model: Linear SVM.** It gives the best balance of precision and recall on the
fraudulent class — Random Forest has perfect precision but misses 43% of actual fraud
cases (too conservative for a *safety-relevant* screening tool), while Logistic Regression
over-flags legitimate postings (precision only 53%). Linear SVM catches ~75% of fraudulent
postings while keeping false alarms low (~9 in 100 flagged postings are false positives).

Confusion matrix (Linear SVM, on the 3,576-row test set):

```
                 Predicted: Legit   Predicted: Fraud
Actual: Legit         3,390                13
Actual: Fraud            44               129
```

Plots: `outputs/model_comparison.png`, `outputs/confusion_matrix.png` (best model), plus a
per-model confusion matrix for each of the three candidates.

## 11. How to Run

```bash
# 1. Clone/copy the project folder, then install dependencies
pip install -r requirements.txt

# 2. Train the model (only needs to be run once; ~60-90 seconds)
#    This reads data/dataset.csv and writes models/*.pkl + outputs/*.png
python train_model.py

# 3. (Optional) print an evaluation report from the saved metrics
python evaluate_model.py

# 4. (Optional) run the 5 built-in test examples through the live pipeline
python test_examples.py

# 5. Launch the web app
streamlit run app.py
```

The app will open at `http://localhost:8501`. Paste a posting into the text box and click
**ANALYZE INTERNSHIP**.

## 13. Limitations

- Trained on **general job postings** (EMSCAD), not an internship-exclusive dataset (see
  Section 6) — internship-specific scam patterns not well represented in the ~866
  fraudulent examples may be missed.
- The dataset covers postings from **2012–2014**; newer scam patterns (e.g. crypto-payment
  requests, QR-code scams) are not represented in training data.
- Rule-based indicators use **fixed keyword/threshold heuristics**; they can miss cleverly
  worded scams and can occasionally trigger on legitimate but informally worded postings
  (e.g. a genuine early-stage startup that also uses WhatsApp for contact).
  During our own testing (`test_examples.py`), a purely urgency-worded scam example (Test
  #4) was scored **LOW RISK** by the model even though rule-based indicators fired — showing
  the system is not infallible and should never be the sole basis for a decision.
- Class imbalance (95%/5%) means the model still produces some false positives and false
  negatives even after using `class_weight="balanced"` (see confusion matrix above).
- The system analyzes **text only**; it cannot verify a company's legal registration,
  physical existence, or reviews.

## 14. Ethics, Social & Environmental Responsibility

- **False positives:** A genuine posting may be flagged MEDIUM/HIGH risk. The UI never
  states a company "is fake" — only that "suspicious characteristics were detected" and
  recommends independent verification, to avoid unfairly damaging a legitimate employer's
  reputation (avoiding defamatory claims).
- **False negatives:** No system catches all fraud. The disclaimer makes clear this is a
  *preliminary* screen, not a guarantee, so users are not lulled into false confidence.
- **Bias in training data:** EMSCAD postings are sourced primarily from Workable (a US/EU
  recruiting platform, 2012–2014); regional scam patterns common in other markets (e.g.
  India-specific fee-scam phrasing) may be under- or over-represented. This is mitigated
  partly by the rule-based indicator layer, which was designed with locally common patterns
  (₹, "WhatsApp", "registration fee") in mind, but should be iteratively improved with more
  regionally diverse data.
- **Privacy:** The prototype does not store, log, or transmit any pasted posting text —
  every analysis happens in-memory for that session only.
- **Avoiding defamatory claims:** Output language is deliberately hedged ("suspicious
  indicator detected", "requires verification") — the system never asserts a specific
  company is fraudulent.
- **Human verification required:** The UI disclaimer explicitly tells users this is not a
  legal determination and independent verification is required before making any decision
  (e.g. paying a fee or sharing documents).
- **Environmental:** Classical ML models (no deep learning/LLMs) were chosen partly because
  they train in under two minutes on a laptop CPU with negligible energy use compared to
  training/running a neural network or calling a hosted LLM for every request.

## 15. Future Scope

- Collect a labeled, internship-specific, India-focused dataset (e.g. via a moderated
  crowdsourced reporting tool) to retrain and reduce the general→internship domain gap.
- Add a browser extension that runs this pipeline directly on internship listing pages.
- Incorporate company-verification signals (e.g. domain age, registration lookup APIs) as
  additional structured features, with appropriate consent/privacy handling.
- Periodically retrain on newer data to capture evolving scam language.
- Add multilingual support (Hindi and other regional languages) for wider applicability.
